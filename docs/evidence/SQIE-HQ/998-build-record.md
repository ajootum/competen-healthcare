**Application order:** 997, then 998. It is independent of 995 and 996.

**Why a migration.** The existing decision record (`clinical_review_decision`: version, reviewer, appointment, decision,
comment) has no place for a separate, explicit approval of the markers. Free-text comments cannot be relied on. 998 adds one
column to that same row, so the approval stays with the reviewer's own decision. The 395/442 guards already bind that row to
the exact version and content hash, and check independence, authority, scope and staleness. Nothing about those guards
changes.

**What it adds** (additions only; no existing function is replaced):
1. **The column** `clinical_review_decision.safety_markers_approved`: boolean, not null, default false. Every earlier decision
   reads false.
2. **`ckri_question_has_safety_markers(content)`.** A revision question carries markers when any of these holds:
   - `answerKey.safetyCritical` is true;
   - `unsafe` is a non-empty list;
   - `safetyCriticalPoints` is a non-empty list;
   - a structured part is safety-critical, lists unsafe answers, or has a safety-critical criterion.
   It is the same rule as `hasSafetyMarkers` in `src/lib/knowledge/safety-markers.ts`; VERIFY-998 checks both on one sample list.
3. **Trigger `clinical_review_decision_marker_guard`** (BEFORE INSERT). It refuses the confirmation unless the decision is an
   approval of a library revision question whose reviewed content carries markers.
4. **`ckri_library_caps_approved(version)`** (security definer, service role only). It is true only when the version:
   - is PUBLISHED;
   - is clinically approved on its current content (`ckri_knowledge_approved`);
   - carries markers;
   - has at least the required number of approving decisions on that exact content that confirmed the markers;
   - has no rejection.

**Rollback:** `ROLLBACK-998.sql` drops the four additions. It refuses while any decision records a marker approval, because
those are reviewers' recorded decisions. Staging now holds 2, from the walk, on retired walk items. Without 998, Scholar caps
nothing.

   submission follow.
2. The review page's rule asks for the confirmation, and lists each marker with its scope: "Safety-critical answer, missing or
   getting it wrong earns 0% of the question" and "Unsafe answer: ..., at most 50% of the question".

   - the confirmation on a rejection is refused: "Safety markers are approved only together with an approval of the version";
   - A is approved WITHOUT the confirmation;

## What the application does

**HQ:**
- **Review page.** `src/app/super-admin/research/knowledge-review/page.tsx` shows the confirmation (approved / not approved,
  required) only for a revision question with markers, beside a list of each marker and its scoring scope
  (`safetyMarkerScopes`).
- **Route.** `POST /api/hq/clinical-review` takes `safetyMarkers: "approved"`. It refuses the confirmation with a rejection,
  and audits it.
- **Decision.** `decideReview` writes it on the same decision row, only when true, so every other decision is written as
  before.

**Scholar:**
- **The gate.** `src/lib/individual/scholar/safety-caps.ts` `questionCapPolicy` returns caps only when all three hold:
  - the switch `scholar_clinical_scoring_caps` is on;
  - the question is a library copy;
  - `ckri_library_caps_approved` is true.
  A failed read, or 998 absent, caps nothing. With the switch off, nothing is read.
- **Revision answers.** The single-answer and structured paths take their caps from the gate.
- **Scenarios.** A scenario is never a library copy, so it is formative.
- **Library clinical-case sessions are never capped.** Case review has no marker approval, so their flags are recorded and
  shown, uncapped. Giving cases the same confirmation would be a follow-up.
